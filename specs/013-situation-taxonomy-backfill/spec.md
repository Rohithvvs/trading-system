## Clarifications

### Session 2026-07-21

- Q: What is the expected volume of historical recommendations in the analysis_histories table that the backfill must process? → A: 100,000 to 1,000,000 records (Medium volume; requires optimized batching and database indices).
- Q: Who is authorized to trigger, pause, resume, or terminate the historical backfill process? → A: Only authenticated users with Administrator privileges (matching the AGENTS.md Phase 0 scope).
- Q: How should the backfill engine store and track the progress of the run to ensure idempotency and clean resumption? → A: Persistent database progress table (Tracks job ID, status, last processed record cursor, and volume statistics).
- Q: Is dynamic, real-time modification of the situation taxonomy rules in-scope for this feature? → A: Out of scope: Taxonomy rules are static/configuration-based; editing rules requires a standard code/config change, and re-applying them requires a manual backfill command trigger.
- Q: How should visibility into the tag distribution (counts and percentages) be exposed to analysts and administrators? → A: CLI command (e.g., experiment.report or a new taxonomy sub-command) that prints the distribution table to stdout and saves a Markdown summary file to a reports directory.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Automatic Ongoing Tagging (Priority: P1)

As a quantitative risk officer, I want every new recommendation generated by the live engine to be immediately tagged with the correct situation tags when it is saved, so that I can perform ongoing, situation-aware performance validation on real-time trade signals.

**Why this priority**: Crucial for operational parity; ensures all future trade signals are natively tagged and immediately available for situation-aware analysis.

**Independent Test**: Generate a recommendation using the live engine under a simulated market regime. Verify that the recommendation is successfully persisted with the correct situation tags automatically applied.

**Acceptance Scenarios**:

1. **Given** the live trading engine is active and generates a new recommendation, **When** the recommendation is saved, **Then** the record is populated with one or more tags matching the current market situation.
2. **Given** a new recommendation is generated during a market situation that does not match any of the defined situational criteria (GOOD_NEWS_CATALYST, BAD_NEWS_CATALYST, EARNINGS_PLAY, MARKET_REGIME, RANGE_BOUND), **When** it is saved, **Then** it is assigned the `UNKNOWN` tag.

---

### User Story 2 - Controlled Historical Backfill (Priority: P1)

As a system administrator, I want to execute a retroactive backfill that assigns the correct situation tags to all existing records in the historical analysis dataset without blocking the live trading engine or causing database connection timeouts.

**Why this priority**: Essential to establish a baseline dataset for validating new models against historical performance under varying market regimes.

**Independent Test**: Run the backfill process on a database containing untagged historical recommendations while simultaneously executing live-style queries and inserts. Verify that the historical records are successfully updated in controlled batches and that the live transactions execute without delays, locks, or failures.

**Acceptance Scenarios**:

1. **Given** the historical analysis histories contain records without situation tags, **When** the backfill is executed, **Then** records are processed in controlled, non-blocking intervals so that database connection limits and transaction locks are never saturated.
2. **Given** the backfill process is running, **When** a manual or system interruption occurs (e.g., operator cancellation, service restart), **Then** the process terminates cleanly without data corruption.
3. **Given** a previously interrupted backfill job, **When** the backfill is restarted, **Then** it resumes from the exact progress marker, processing only the remaining untagged or partially tagged records.

---

### User Story 3 - Tag Distribution and Analytical Querying (Priority: P2)

As a quantitative analyst, I want to view the distribution of situation tags across the entire dataset and query recommendations filtered by specific situation tags and actions, so that I can validate that the taxonomy is well-balanced and perform segment-specific backtests.

**Why this priority**: Provides the visibility needed to confirm the backfill's quality and enables the primary business use case: situation-aware model validation.

**Independent Test**: Execute a query to view the distribution of tags across all recommendations, and run a compound query to filter recommendations by situation tag, action, and date range. Verify the results return correct counts and correct record matches.

**Acceptance Scenarios**:

1. **Given** the backfill has processed historical records, **When** the tag distribution is requested, **Then** the system returns a summary showing the exact counts and percentage share of each tag (GOOD_NEWS_CATALYST, BAD_NEWS_CATALYST, EARNINGS_PLAY, MARKET_REGIME, RANGE_BOUND, UNKNOWN) relative to the total dataset.
2. **Given** an analyst queries recommendations by situation, action, and date range (e.g., "all GOOD_NEWS_CATALYST BUY recommendations in the last 6 months"), **When** the query is run, **Then** the system returns only the records that meet all the specified criteria.

### Edge Cases

- **Corrupted or Incomplete Historical Records**: If a historical record is missing essential parameters (such as timestamps or reference market data snapshots) required to determine its situation, the backfill engine must assign the `UNKNOWN` tag and log a warning for that specific record rather than failing the entire batch.
- **Interruption Mid-Batch**: If the backfill process is abruptly halted in the middle of updating a batch, the system must ensure that database transactions roll back cleanly, or that the resumption mechanism can handle partially updated batches without duplicating tags.
- **Overlapping/Multi-Tag Matches**: If a recommendation meets the criteria for multiple situations (e.g., both `EARNINGS_PLAY` and `GOOD_NEWS_CATALYST`), the system must support assigning multiple tags to the same record without error.
- **Database Resource Throttling**: Under high live system load, the backfill process must allow manual pausing or self-throttle to prioritize live trading engine operations.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 (Ongoing Automatic Tagging)**: The system MUST automatically evaluate and assign the correct situation tags to every new recommendation at the moment it is created and persisted by the live trading engine.
- **FR-002 (Taxonomy Definition)**: The system MUST support the classification of recommendations into one or more of the following situation tags:
  - `GOOD_NEWS_CATALYST`
  - `BAD_NEWS_CATALYST`
  - `EARNINGS_PLAY`
  - `MARKET_REGIME`
  - `RANGE_BOUND`
  - `UNKNOWN`
- **FR-003 (Taxonomy Uniformity)**: The classification logic used to determine situation tags MUST be deterministic, explainable, and applied identically to both historical backfills and ongoing live tagging.
- **FR-004 (Controlled Batch Backfill)**: The system MUST provide an administrative capability, restricted to authenticated users with Administrator privileges, to retroactively assign situation tags to all existing records in the analysis history. This process MUST run in controlled batches, releasing locks between updates to prevent table locks and database connection timeouts.
- **FR-005 (Resumability)**: The backfill process MUST persist progress markers (such as job status, last processed record cursor, and statistics) in a database-level progress tracking table, allowing it to resume cleanly from the point of interruption if paused or stopped.
- **FR-006 (Distribution Reporting)**: The system MUST provide a CLI command interface to output the overall situation tag distribution (counts and percentages) to stdout and save a Markdown summary report in a designated reports directory.
- **FR-007 (Situation Filtering)**: The system MUST support querying and filtering recommendations by one or more situation tags, recommendation action, and date range.
- **FR-008 (Fallback Tagging)**: If a recommendation does not satisfy any of the specific situational taxonomy rules, the system MUST assign it the `UNKNOWN` tag.

### Key Entities *(include if feature involves data)*

- **Analysis History / Recommendation**:
  - Represents a persisted recommendation generated by the trading system.
  - Key Attributes: `recommendation_id` (unique identifier), `symbol` (string), `action` (e.g., BUY, SELL), `timestamp` (datetime), `situation_tags` (list of strings matching the taxonomy).
- **Backfill Progress Marker**:
  - Tracks the state and progress of the historical backfill process.
  - Key Attributes: `job_id` (string), `last_processed_timestamp` (datetime), `last_processed_id` (identifier), `status` (enum: IDLE, RUNNING, PAUSED, COMPLETED), `processed_records` (integer), `total_records` (integer).
- **Situation Taxonomy Rule**:
  - Represents the deterministic logic mapping market contexts to situation tags.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of historical recommendations in the analysis history are retroactively assigned one or more situation tags.
- **SC-002**: Every new recommendation generated by the live engine automatically receives its situation tags at the moment of creation.
- **SC-003**: The backfill runs to completion during low-traffic periods without causing table locks, database connection timeouts, or any disruption to live trading engine queries.
- **SC-004**: The resulting situation tag distribution is healthy and useful for validation:
  - No single tag (excluding `UNKNOWN`) exceeds 60% of the entire dataset.
  - The `UNKNOWN` tag is assigned to less than 15% of the total dataset.
- **SC-005**: Compound analytical queries filtering recommendations by situation tag (e.g., "show GOOD_NEWS_CATALYST BUYs in the last 6 months") return complete and accurate results in under 2 seconds.

---

## Assumptions

- **Market Context Availability**: The historical data in the database contains sufficient contextual information (e.g., prices, signals, or referenced market indicators) to allow the deterministic rules to evaluate situation tags retroactively.
- **Database Write Capacity**: The database has sufficient capacity to handle batch updates during low-traffic periods without impacting the concurrent read operations of other services.
- **Indexing Support**: The database structure supports indexing or efficient querying on the situation tag field/relation to meet the analytical response time criteria.
- **Single Master Control**: Only one backfill job is run at any given time, preventing race conditions or double-tagging.
- **Historical Dataset Volume**: The historical analysis history dataset is of medium volume (100,000 to 1,000,000 records), requiring optimized batching and database indexing to prevent locks and latency degradation.
- **Static Taxonomy Rules**: The rules defining the situation taxonomy are static and defined in code/configuration; runtime modification of rules via database or API endpoints is out of scope for this feature.
