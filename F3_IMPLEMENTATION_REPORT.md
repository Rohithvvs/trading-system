# F3 Implementation Report: Shadow Run Validation Preparation

## Objective
The goal of this implementation is to establish automated, robust evidence collection for the Monday shadow run, covering scanner executions, scheduler tasks, external dependencies (FYERS), and database health—all without mutating core business or trading logic.

## Changes Implemented

### 1. Runtime Evidence Collector (Diagnostics Service)
- **File**: `backend/app/services/diagnostics_service.py`
- Extensively modified the `ShadowRunDiagnostics` class to collect structured, pre-calculated payload summaries mapping directly to Phase F.3 requirements.
- Implemented `get_shadow_run_report(self, db)` generating the comprehensive JSON representation of all internal system metrics.

### 2. Shadow Run Reporting Endpoint
- **File**: `backend/app/routes/system.py`
- Added the `GET /system/shadow-run/report` endpoint.
- Connects directly to the structured diagnostic summaries generated by `diagnostics_service.py`.

### 3. Scanner Metrics Alignment
- **File**: `backend/app/main.py`
- Refactored `diagnostics.record_scanner_run` field mappings inside `automated_screening_job` to exactly align with requirements:
  - `start_time`, `end_time`, `duration_ms`
  - `requested_symbols`
  - `valid_symbols`
  - `buy_count`, `watch_count`, `rejected_count`
  - `exception_count` (Mapped gracefully via skip/duplicate events).

### 4. Scheduler Metrics Alignment
- **File**: `backend/app/main.py`
- Updated `_scheduler_listener` hooking `EVENT_JOB_EXECUTED | EVENT_JOB_ERROR | EVENT_JOB_MISSED`.
- Added logic resolving the `success` (Boolean) flag and dynamic mapping for `failure_reason` reading directly from `event.exception`.

### 5. Database Health Tracking
- Augmented the `get_db_health()` lookup inside the diagnostics core.
- Injects dynamic schema checks against PostgreSQL retrieving exact `scan_snapshot_count` and `scan_snapshot_record_count` in real-time.
